# glean — Insigmind 活跃度自动统计

一个 Go 写的常驻小工具，每小时采集 Insigmind 平台的**累计寻源 / 累计触达 / 需求总量**三个指标，算出增量活跃度，自动生成日报/周报/月报/年报并通过邮件发送。单二进制 + YAML 配置，零外部依赖（除 `gopkg.in/yaml.v3`），可部署在 Linux 服务器甚至 mipsle 架构的极路由 2 上。

---

## 采集指标 & 数据源

两个接口，每小时拉取一次，对比上一条记录计算**增量**：

| 指标 | 来源 | 字段 |
|------|------|------|
| 累计寻源次数 | 首页统计接口 | `data.searchCount` |
| 累计触达次数 | 首页统计接口 | `data.contactCount` |
| 需求总量 | 需求列表接口 | `data.totalCount` |

**接口详情：**

1. 首页统计接口（GET）
   - URL: `https://api.insigmind.com/Api/WebLogin/GetIndexStats`

2. 需求列表接口（POST, `Content-Type: application/json`）
   - URL: `https://api.insigmind.com/Api/WebDemand/SearchDemands`
   - 请求体固定查询条件，只取 `totalCount`：
     ```json
     {"pageSize":10,"total":0,"pageNumber":1,"demandUrban":"","demandExpirationDate":"",
      "newDate":"","sortFieldName":"AuditProperties.CreateAt","sortDirection":"Descending","demandStatus":1}
     ```

> **容错策略：**
> - 需求接口采集失败不致命：打印警告后沿用上一次的值，本次增量按 0 计。寻源/触达照常入库。
> - 累计值出现回退（接口数据重置）时，增量按 0 计并在报告中标注警告。
> - 主接口连续返回 HTTP 404 时触发告警邮件（见「接口告警」）。

## 快速开始

### 构建

```bash
go build -o glean main.go
```

手动注入版本号（建议东八区时间戳，不破坏 `-ldflags` 参数切分）：

```bash
go build -ldflags "-X main.version=$(TZ=Asia/Shanghai date +'%Y-%m-%d_%H-%M-%S')" -o glean main.go
```

未注入时版本号为 `dev`。程序启动和日志中会打印版本号，可 `grep "version="` 检索当前运行版本。

### 运行

```bash
glean                  # 常驻：立即采集一次 + 生成启动报告，之后每小时整点自动采集
glean --once           # 仅采集一次后退出（适合配合系统计划任务）
glean -debug           # 开启调试日志（可与其他参数组合）
glean -version         # 打印版本号后退出
glean -mail            # 发送一封测试邮件后退出
glean -report=2026-09-01        # 手动生成日报
glean -week=2026-09-03          # 手动生成周报
glean -month=2026-08            # 手动生成月报
glean -year=2026                # 手动生成年报
glean -startup-report=false     # 关闭启动时自动生成的 4 份报告（默认开启）
glean -config=/path/to/config.yaml  # 指定配置文件（默认工作目录下的 config.yaml）
```

## 时区：统一东八区

程序内部**全链路使用东八区（Asia/Shanghai / UTC+8）**，与运行环境所在系统时区无关：

- 采集时间戳、日志每行时间戳、日志文件名（按天切分）、每天的报告调度时刻、周/月/年周期判定，均以东八区为准。
- 优先读取系统时区数据库中的 `Asia/Shanghai`；若运行环境无 tzdata（如精简路由器固件），自动退化为固定 `+08:00` 偏移。两种情况下行为一致。
- 标准库 `log` 包的前缀时间固定使用系统本地时区（UTC 机器上会打印 UTC），因此程序通过自定义 `cstLogWriter` 接管时间戳：关掉 `log` 自带时间（`log.SetFlags(0)`），改由写入时补东八区时间，控制台与日志文件口径完全一致。
  ```
  2026/09/02 09:23:31 采集成功 [2026-09-02 09:23:31] 累计寻源=118837 累计触达=18164
  ```

**调度机制：** 每轮循环同时计算「下一个整点（采集）」与「下一个报告时刻」，取较早者作为唤醒点。因此报告时刻可以是任意 `HH:MM`（不必整点），且改 `config.yaml` 后**下一轮调度即生效，无需重启**。

## 报告系统

四种报告写入 `./reports/` 目录（按子目录分），统一使用字符条形图展示增量活跃度，最大值带 ⚠️ 标记。**`reports/` 每天都会重新滚动更新到最新数据，但邮件按原周期发送**——不会因为"每天都刷新"而每天收到 4 封邮件。

### 汇总区块

| 报告 | 汇总内容 |
|------|----------|
| 日报 | 【当日汇总】：`起始基准(前一日23:00) → 期末值(当日23:00)` 的总增量，覆盖当天 `00:00~23:59` 全部增量；首日运行退化为以当日首条记录为基准 |
| 周报 | 【本期汇总】：合计增量 + 日均增量 |
| 月报 | 同周报 |
| 年报 | 【本期汇总】：合计增量 + **月均**增量 |

### 高峰/低峰分析

每个报告都会为三个指标分别找出**增量最大的时段（高峰）**与**最小的时段（低峰）**，并列时段全部列出（超过 3 个时截断注明"等共 N 个"）：

| 报告 | 分析粒度 | 示例 |
|------|----------|------|
| 日报 | 几点 | `高峰 19:00 (+276) \| 低峰 03:00 (+0)` |
| 周报 | 周几 | `高峰 周六 (+512) \| 低峰 周日 (+88)` |
| 月报 | 具体日期 | `高峰 09-05 (+320) \| 低峰 09-12 (+41)` |
| 年报 | 月份 | `高峰 2026-05 (+4200) \| 低峰 2026-02 (+800)` |

### 年报专属：全年每日热力图

年报额外输出三张**全年每日热力图**（三个指标各一张），用 5 级亮度的点字字符（`⠂ ⣀ ⣄ ⣶ ⣿`）把每天增量画成年历图：

```
【全年每日热力图】(指标: 累计寻源次数, 单位: 次)
  2026年
01月|⣶⠂⠂⠂⣶|⠂⣶⠂⠂⣶|⣶⠂⣶⣄⠂|⣀⠂⣀⠂⣶|⠂⣀⠂⣶⠂|⠂⠂⠂⠂⠂|⣀⠂⠂⠂⠂
02月|⠂⠂⠂⠂⠂|⠂⠂⠂⠂⠂|⠂⣀⣄⠂⠂|⠂⠂⠂⠂⠂|⠂⣀⠂⠂⣄|⠂⠂⠂⠂⠂|⠂⠂⠂⠂⠂
03月|⠂⣶⠂⠂⠂|⠂⠂⣀⠂⠂|⠂⠂⣄⣀⠂|⣶⣶⠂⠂⣄|⠂⠂⠂⠂⣄|⠂⠂⠂⣀⠂|⣀⠂⠂⠂⠂
...
  Less ⠂ ⣀ ⣄ ⣶ ⣿ More (按全年单日最大增量 988 次 归一化)
```

- 每行一个月（`01月` ~ `12月`），固定 35 字符 = 7 组 × 5 天，`|` 分隔，便于对照日历
- 亮度 = 当天增量 / **该指标全年单日最大值**，无增量或超出当月天数的位置显示最浅的 `⠂`
- 只看相对高低，绝对数值仍以汇总与条形图为准

### 报告生成时机

| 报告 | 文件路径 | 自动触发时机 | 邮件发送 |
|------|----------|--------------|----------|
| 日报 | `daily/YYYY-MM-DD_report.txt` | 每天东八区 **05:00**（可改）自动生成前一天 | 每天一封 |
| 周报 | `week/week_YYYY-MM-DD_report.txt`（周一日期） | **每天**刷新文件 | 前一天为周日时发送 |
| 月报 | `month/month_YYYY-MM_report.txt` | **每天**刷新文件 | 前一天为月末时发送 |
| 年报 | `year/year_YYYY_report.txt` | **每天**刷新文件 | 前一天为 12/31 时发送 |

> 所有时刻均为东八区，由 `config.yaml` 的 `report.time` 决定（默认 `05:00`）。

### 启动报告

程序启动时（非 `-once` 模式）会先把 4 类报告全部刷新一遍，默认**只更新文件并打印到日志，不发邮件**。由 `report.startup_mail` 控制：

- `startup_mail: false`（默认）：启动只更新文件 + 日志，避免每次重启都收到 4 封邮件
- `startup_mail: true`：启动即发送 4 封报告邮件

启动报告的参考日期选定规则：历史有"昨天"数据时以昨天为准，否则退化为历史中最后有数据的日期，保证仍能出一份有效报告。

报告完整内容会打印到运行日志（控制台 + `logs/glean_YYYY-MM-DD.log`），无需打开 `reports/` 下的文件。

### 日报示例

## 接口告警

当首页统计接口（主接口）**连续返回 HTTP 404** 达到阈值时，程序会自动发送紧急告警邮件。接口恢复正常后（默认）再发一封恢复通知邮件。

**告警状态**保存在 `alert_state.json`，跨进程重启累计不丢失。

### 触发条件

- 主接口返回 HTTP 404（`err == nil && statusCode == 404`）时连续计数 +1
- 请求完全失败（网络错误等 `statusCode == 0`）或返回其他错误码**不计入**连续计数
- 达到阈值且尚未发过告警时，发送告警邮件

### 恢复条件

- 主接口返回 200 成功时：重置连续计数 → 发送恢复通知（若之前发过告警）

### 告警配置（`config.yaml` 的 `alert` 段）

| 字段 | 默认值 | 说明 |
|------|--------|------|
| `enabled` | `true` | 告警开关 |
| `consecutive_404_threshold` | `48` | 连续 404 次数阈值。默认 48 次 = 2 天 × 每天 24 次采集；改成 `24` 即"连续 1 天 404 就告警" |
| `notify_recovery` | `true` | 告警后接口恢复正常时，是否再发一封恢复通知邮件 |

### 告警邮件示例

**告警主题：** `🚨🚨🚨🚨🚨 公司倒闭了！接口连续 48 次返回 404（约 2.0 天）`

**告警正文摘要：**
```
紧急告警：公司可能倒闭了！
接口持续返回 HTTP 404，已连续 48 次（约 2.0 天，按每小时一次采集计算）。
```

**恢复主题：** `✓ 接口恢复正常（此前连续 48 次 404）`

## 配置文件（config.yaml）

启动时读取**工作目录下**的 `config.yaml`，可用 `-config` 指定其他路径。

**自动处理：**
- 文件不存在 → 自动生成带注释的默认配置文件，本次运行使用默认值
- 文件为空 → 同样自动补写默认配置
- 字段缺失/为空 → 仅该字段回退到默认值
- 读取/解析失败 → 整体回退到默认配置，不中断运行

### 默认配置示例（首次运行自动生成）

```yaml
mail:
  smtp_host: smtp.qq.com          # SMTP 服务器
  smtp_port: 465                  # 端口：465=隐式 TLS，587=STARTTLS
  from: 768305875@qq.com          # 发件邮箱
  auth_code: xxxxxxxx             # 授权码（非登录密码）
  to: 768305875@qq.com            # 收件邮箱，多个用 , 或 ; 分隔
  subject_prefix: '【业务监控】'   # 主题前缀，留空则不加；以 [ 开头时必须加引号
  skip_verify: true               # 是否跳过 TLS 证书校验

report:
  time: '05:00'                   # 每天生成定时报告的时刻（东八区 HH:MM），支持分钟
  periodic_mail: true             # 每天定时生成的报告是否发送邮件
  startup_mail: false             # 启动报告是否发送邮件

alert:
  enabled: true
  consecutive_404_threshold: 48   # 连续多少次 HTTP 404 后触发告警
  notify_recovery: true           # 恢复正常时是否发送恢复通知邮件
```

### 环境变量覆盖

**优先级：环境变量 > config.yaml > 内置默认值**

| 环境变量 | 对应字段 |
|----------|----------|
| `GLEAN_SMTP_HOST` | `smtp_host` |
| `GLEAN_SMTP_PORT` | `smtp_port` |
| `GLEAN_MAIL_FROM` | `from` |
| `GLEAN_MAIL_AUTH` | `auth_code` |
| `GLEAN_MAIL_TO` | `to` |
| `GLEAN_MAIL_SUBJECT_PREFIX` | `subject_prefix` |
| `GLEAN_MAIL_SKIP_VERIFY` | `skip_verify`（`1`/`true` 表示跳过） |

### 邮件主题

由「前缀 + 报告名」组成，例如前缀为 `【业务监控】` 时：
- 日报：`【业务监控】 日报 2026-09-05`
- 周报：`【业务监控】 周报 2026-08-31 ~ 2026-09-06`
- 月报：`【业务监控】 月报 2026-08`
- 年报：`【业务监控】 年报 2026`

> 注意：YAML 中以 `[` 开头的字符串必须用引号包住（如 `subject_prefix: '[glean]'`），否则会被当成数组导致解析失败。

## 邮件发送

基于 `net/smtp` 的邮件发送实现：
- 465 端口 → 隐式 TLS 直连；其他端口（如 587）→ 先连接再 STARTTLS 升级
- 中文主题自动做 RFC2047 编码，正文为 UTF-8 纯文本
- 连接/交互超时 15 秒，避免网络异常挂起
- 配置 `skip_verify: true` 时跳过 TLS 证书校验（部分网络环境证书链不完整时需要）

```go
SendMail("标题", "正文")                // 使用 config.yaml / 环境变量 / 默认值
SendMailWithConfig(cfg, "标题", "正文") // 使用自定义配置
```

验证 SMTP 配置：
```bash
glean -mail            # 发送一封测试邮件后退出
glean -mail -debug     # 附带 SMTP 交互调试日志
```

## 守护脚本部署（Linux / 路由器插件）

`startup.sh` 是一个完整的守护脚本，功能包括：启动前清理残留进程、等待网络就绪、从 GitHub 下载/热更新二进制、进程崩溃后指数退避重启（5s→300s）、PID 防重复启动、优雅停机、下载重试。

部署目录：`/plugins/data/glean`（脚本会 `cd` 到此目录，程序的数据文件均生成于此）。

```bash
chmod +x startup.sh
./startup.sh                           # 前台运行
nohup ./startup.sh > /dev/null 2>&1 &  # 后台运行
```

脚本顶部「配置区」可调整的关键参数：

| 变量 | 默认值 | 说明 |
|------|--------|------|
| `PLUGIN_DIR` | `/plugins/data/glean` | 插件与数据目录 |
| `BINARY_NAME` | `glean` | 二进制文件名 |
| `DOWNLOAD_URL` | `github.com/.../default.glean_linux_mipsle` | 下载地址 |
| `UPDATE_INTERVAL` | `14400`（4 小时） | 更新检查间隔（秒） |
| `MAX_RETRY` | `20` | 下载最大重试次数 |
| `RESTART_DELAY` | `5` | 崩溃重启初始延迟（秒），指数退避 |
| `MAX_RESTART_DELAY` | `300` | 崩溃重启最大延迟（秒） |
| `CONNECT_TIMEOUT` | `120` | curl 连接超时（秒） |
| `MAX_DOWNLOAD_TIME` | `1200` | curl 单次下载最大耗时（秒） |
| `GRACEFUL_SHUTDOWN_TIMEOUT` | `10` | 热更新/停止时等待程序优雅退出的超时（秒） |

### 热更新机制

1. 启动后立即尝试下载一次，发现新版本则替换并重启
2. 后续按 `UPDATE_INTERVAL` 定期检查
3. 下载后用 `cmp -s` 比对文件，一致则跳过替换
4. 替换流程：停程序 → 删旧二进制 → 重命名临时文件 → 启动新版本

更新记录文件 `.last_update_check`（4 字段，兼容旧格式自动升级）：
```
时间戳|人类可读时间戳|下次检查时间戳|下次检查人类可读时间戳
```
例如：`1756792345|2026-09-02 09:23:45 CST (UTC+0800)|1756806745|2026-09-02 13:23:45 CST (UTC+0800)`

### 脚本运行时产物

- `logs/glean.log` — 脚本日志（启动/更新/重启等守护行为）+ 程序 stdout
- `glean.pid` — 守护脚本自身的 PID 文件
- `.last_update_check` — 更新时间戳记录
- `glean` — 主程序二进制
- 程序自身数据文件：`logs/`、`reports/`、`sql/`、`stats_history.json`、`sql/stats_log.csv`

> 脚本必须使用 **LF 换行**（若经 Windows 编辑需 `dos2unix startup.sh`）。

## GitHub Actions 构建

`.github/workflows/build.yml` 在推送到 `main` 分支时自动构建 4 个平台的二进制，并发布到 `dev-latest` Release：

| 目标 | 说明 |
|------|------|
| Linux mipsle | 极路由 2 架构，CGO_ENABLED=0 + 静态编译 |
| Linux amd64 | 通用 x86_64 服务器 |
| Linux arm64 | ARM 服务器 |
| Windows amd64 | Windows 可执行文件 |

Release 使用固定 tag `dev-latest`（每次构建删除重建），方便 `startup.sh` 的下载地址长期稳定可用。

## 项目文件结构

```
glean/
├── main.go              # 采集逻辑 / 报告生成 / 调度循环
├── config.go            # YAML 配置加载 / 时区 ClockTime 解析
├── mail.go              # SMTP 邮件发送（隐式 TLS + STARTTLS）
├── alert.go             # 接口 404 连续告警 & 恢复通知
├── go.mod / go.sum
├── config.yaml          # 用户配置（首次运行自动生成）
├── startup.sh           # Linux 守护脚本 + 热更新
├── .github/workflows/build.yml  # CI 构建 & Release
└── README.md
```
